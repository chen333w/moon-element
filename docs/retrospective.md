# 开发复盘

日期：2026-10-22 ｜ 模块：`chen333w/moon-element` ｜ 工具链：`moon 0.1.20261020`

这份文档记录**关键决策**与**过程中真实出错的地方**。后者比前者更有价值：
一个项目的质量，往往体现在「错误是怎么被发现的」。

## 1. 目标

让 MoonBit 能产出**标准 Web Components**——组件以 `customElements.define` 注册，
可嵌入任意网页或框架，不引入任何 MoonBit 侧的前端框架运行时。

## 2. 关键决策

每一项写清「选择 / 否掉的方案 / 为什么 / 事后看」。

### 2.1 切成 `core`（纯逻辑）与 `dom`（js 适配层）

- **选择**：属性反射、生命周期、渲染、CSS 作用域、事件规则全部放 `core`；`dom` 只做 DOM 接线。
- **否掉**：全部放一个 js-only 包（更省事）。
- **为什么**：这个项目真正容易错的是**规则**（非法属性值怎么回退、重复连接要不要重复触发、
  事件要不要 `composed`），不是接线。规则放 `core` 就能在四个后端跑普通单元测试，
  不需要浏览器；`dom` 里只剩「有没有接对」。
- **事后看**：对。四后端 61 个测试绝大多数是 `core` 的，快照测试还抓到了真 bug（见 4.1）。

### 2.2 js FFI 用普通函数类型而不是 `FuncRef`

- **选择**：`extern "js"` 的回调参数声明为 `() -> Unit`（允许捕获）。
- **否掉**：`FuncRef[() -> Unit]`（无捕获闭包）。
- **为什么**：第一版编译失败（错误码 4014）——`FuncRef` 要求无捕获，而适配层必须把
  `specs` 与用户的 `render_fn` 捕获进回调。FFI 文档对 JS 后端明确写着
  「JavaScript supports closure, so there's nothing special to be done here」。
- **事后看**：对；该前提由 8 个适配层测试持续验证。若将来把这一层复用到 Wasm 后端，
  必须重新评估（那时需要 `FuncRef` + `make_closure`）。

### 2.3 跨 FFI 不传 `Option`

- **选择**：老值/新值用「存在性 `Bool` + `String`」两个参数传。
- **否掉**：直接传 `String?`。
- **为什么**：`Option` 的跨 FFI 表示不是稳定 ABI；`Bool`/`String` 则是文档列明的。
  这种地方「看起来能跑」，换后端或版本就可能静默错。
- **事后看**：对，代价只是参数变长。

### 2.4 实例状态每次写回，不依赖结构体别名语义

- **选择**：取出状态 → 修改 → 写回注册表。
- **为什么**：不确定 MoonBit 结构体赋值是引用还是拷贝；无论哪种，写回都正确。
- **事后看**：对，一行代码消除一个不确定性。

### 2.5 渲染整块替换 `innerHTML`，不做 diff

- **选择**：`View` 树 → HTML 字符串 → 写入 shadow root。
- **否掉**：逐元素 diff（工作量与风险大得多）。
- **为什么**：先走通「属性驱动 + 可测 + 可演示」主线。
- **代价（已写进 README 的「已知限制」）**：组件内部不适合挂 DOM 监听器（下次重渲染会换掉），
  因此 demo 的交互按钮放在页面侧。这是当前实现下的正确做法，不是回避。

### 2.6 属性语义对齐 HTML 的宽松行为

- **选择**：属性缺失或值非法 → 回退默认值，不报错；布尔「存在即真」（`"false"` 也是 `true`）。
- **为什么**：这是 HTML 的既定语义；属性反射走严格模式会和用户直觉打架。
- **事后看**：对。「布尔存在即真」反直觉，专门写了测试钉住。

### 2.7 整数解析限制 9 位十进制数字

- **为什么**：`Int` 宽度可能随后端而异。限位数保证「不接受的值一律回退默认值」，
  而不是在某个后端静默溢出、在另一个后端正常——**跨后端行为必须一致**。

### 2.8 生成器产物提交进仓库并被 CI 校验

- **选择**：`examples/generated-x-counter` 由 CLI 实际生成后提交；CI 校验
  「当前 CLI 产出 == 仓库文件」。
- **为什么**：生成器很容易与产物脱节，而这种脱节平时看不出来。
- **事后看**：对，它立刻抓到一个问题（生成器 `println` 多打一个换行，
  与 `moon fmt` 规范化结果永远不一致）。

### 2.9 给 CSS 作用域模块一个真实用途：light DOM 模式

- **发现的问题**：`core/css.mbt`（`scope_css`）有 133/137 覆盖率，却**在适配层和 demo 里
  完全没被使用**——测试很漂亮，但它是死代码。「有测试」不等于「有用」。
- **选择**：给 `define_component` 加 `styles`（组件 CSS 只声明一次）与 `mode`
  （`ShadowDom` / `LightDom`）；light 模式下不建 shadow root，而是先用 `scope_css`
  把 CSS 作用域到标签名再注入。
- **否掉的方案**：删掉 `scope_css`（更省事），或让它继续只被单元测试使用。
- **为什么**：SSR 输出、需要宿主样式透入的场合确实不能用 shadow DOM；而且留着不被使用的
  模块，等于给未来的维护者埋一个"这玩意到底干嘛的"。
- **事后看**：对。顺带把 demo 的样式从视图里搬到了 `styles=`，视图变回纯内容，
  组件定义也更清楚。

## 3. AI 参与方式与质量门禁

代码、文档、CI 配置由 AI 助手编写，方向与验收标准由人给出。**关键在于 AI 的产出
全部经过可执行的门禁**，不是靠"看起来对"：

| 门禁 | 作用 |
| --- | --- |
| `moon check --deny-warn --target all` | 警告即失败 |
| 四后端 `moon test --deny-warn` | 规则必须在 wasm / wasm-gc / native / js 上一致 |
| 内联快照（`inspect`） | 渲染与 CSS 改写输出逐字钉住 |
| `moon info` + `git diff --exit-code` | 公开接口不许悄悄漂移 |
| 生成器漂移检查 | 生成器与产物不许脱节 |
| 产物级验证（`examples/demo/verify.mjs`） | 直接加载构建产物跑断言，不只信单元测试 |
| GitHub Actions（12 步） | 以上全部在干净环境复现 |

## 4. AI 出错并被发现的案例

### 4.1 `:host(.active)` 被错写成 `my-el(.active)`

- **发现**：内联快照测试给出 diff。
- **性质**：`my-el(.active)` 在 CSS 里是**无效选择器**——括号内是复合选择器，
  必须去掉括号接在 scope 后。
- **修复**：重写 `:host(...)` 分支；补 `:host(:is(.a, .b))` 嵌套括号的测试。
- **若不发现**：只会表现为"样式莫名不生效"，极难排查。

### 4.2 测试预期写错了，而实现是对的

- **现象**：断言 `kebab_to_camel("x--_y") == "x_Y"` 失败，实际 `"x_y"`。
- **结论**：连续短横线只触发一次大写动作，该动作被非字母字符**消耗**掉，后面的 `y` 保持小写。
- **处理**：改成钉住真实语义（`x-_y` → `x_y`、`x-_Y` → `x_Y`），而不是迁就直觉。

### 4.3 「必须配置 `link.js.format = "esm"`」——结论是错的

- **复核**：实测加上与不加上该选项，产物**逐字节相同**；产物既无 `export` 也无 `require`。
- **结论**：该选项对可执行包是 no-op；浏览器能用，是因为 `<script type="module">`
  对**无导出的脚本同样有效**。
- **处理**：改文档，并在 `examples/demo/moon.pkg` 里**故意不写**该选项（留着会误导）。

### 4.4 步骤名里的 `": "` 把整个 CI 打崩

- **现象**：本地 `moon check` / `moon test` 全绿，推上去 GitHub 报 *workflow file issue*，
  **一个 job 都没产生**。
- **定位**：`- name: CLI: generated skeleton ...` 中的 `": "` 在 YAML 普通标量里非法。
- **处理**：加引号，并补上「本地校验容器文件」的习惯：
  `ruby -ryaml -e 'YAML.load_file(".github/workflows/ci.yml")'`。
- **教训**：此前只验证了 MoonBit 侧的命令序列，漏了容器文件本身——**验证对象选错了**。

## 7. 覆盖率说明

库本体（`core` + `dom`）行覆盖 **96.3%**（650/675）；计入 CLI 入口与 demo 的整仓数字为
83.8%（650/776）。剩余未覆盖行分三类，**不强行凑 100%**：

1. 防御性分支（索引合法时 `String::get_char` 不会返回 `None`）
2. 内联导致的行号归属偏差（例如 `kebab_to_camel("max-count")` 必然执行 `ascii_to_upper`，
   却仍报该行未覆盖）
3. 集成路径（CLI 入口、demo 注册），由「产物级验证 + 生成器漂移检查 + CI 编译」覆盖
